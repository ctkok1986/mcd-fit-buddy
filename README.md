## 😤 先说一个反直觉的事实

市面上所有"麦当劳减脂助手"都在做同一件事：给你一份看起来合理的低卡餐单。

**但它们几乎都不告诉你：这份餐单哪里是补不上的。**

我们拿官方营养接口的 **158 项餐品数据**做了一次完整的可行域求解，结果是这样：

**一个 78kg / 175cm / 40 岁的男性，目标是 12 周减到 72kg：**

| | 蛋白优先 | 控钠优先 |
|---|---|---|
| 全天热量 | 1846 kcal ✅ | 1857 kcal ✅ |
| 蛋白质 | **128 g**（目标 140） | **92 g**（目标 140） |
| 钠 | **3488 mg** ❌ | **1941 mg** ✅ |

WHO 建议每日钠摄入 **< 2000 mg**。

**两个方案没有一个能同时满足「热量达标 + 蛋白达标 + 钠达标」。**

这不是算法没调好——这是**麦当劳餐单的结构性事实**：菜单里高蛋白的选择（脆汁鸡、安格斯牛堡）钠含量都极高，而低钠的选择（玉米杯、牛奶、美式）热量和蛋白都低。

**本项目的立场：与其给一份粉饰过的餐单，不如把这个矛盾摊开给你看，让你自己选。**

## ✨ 八个能力

### 🎯 一、三种目标模式：减脂 / 增肌减脂 / 增肌

同一个引擎，三种目标模式。**锚点是 TDEE（每日总消耗），不是 BMR。**

```bash
--goal cut      # 减脂（保肌优先）    缺口 18%   蛋白 2.2 g/kg 瘦体重
--goal recomp   # 增肌减脂（体成分重组）缺口  8%   蛋白 2.4 g/kg 瘦体重
--goal gain     # 增肌（小盈余）      盈余  8%   蛋白 2.0 g/kg 瘦体重
```

**为什么要专门说明「不锚定 BMR」**——因为"摄入不超过基础代谢"是个流传很广但危险的做法。实测（BMR = 1600）：

| 活动强度 | TDEE | 若只吃 1600（= BMR） | 判定 |
|---|---|---|---|
| 久坐 | 1920 | 缺口 320（16.7%） | 可行，但减得慢 |
| 轻度 | 2200 | 缺口 600（**27.3%**） | 超 25% 安全上限 → **掉肌肉** |
| 中度 | 2480 | 缺口 880（**35.5%**） | 显著掉肌肉 |
| 高度 | 2760 | 缺口 1160（**42.0%**） | 代谢适应 |

而**增肌需要吃到 BMR 的 1.3~1.7 倍**——"不超过 BMR"这条路数学上到不了。

所以本工具的规则是：**摄入锚定 TDEE，BMR 只作下限护栏**（不低于 BMR×1.1）。
三种模式下输出的摄入目标都**高于 BMR**，并在结果里直接给出对照：

```
【摄入目标对照：为什么不锚定 BMR】
  若按「不超过 BMR」  1600 kcal  → 缺口 600（27.3%）｜已超 25% 安全上限 → 会掉肌肉
  本工具建议摄入      2024 kcal  → 缺口 176（8.0%）｜锚定 TDEE，保住肌肉
```

### 🔬 二、体成分引擎（离"看得见腹肌"还有多远）

填体脂率（或腰围/颈围让工具用海军法估算），算出：

```
体脂率          22.1 %   （海军法（腰92/颈38/身高175）｜误差 ±3~4%）
脂肪量          17.2 kg
瘦体重 LBM      60.8 kg   ← 这个才是「需要蛋白的部分」

当前 22.1% → 极微弱轮廓
目标 12.0% → 上腹可见
需减脂肪        8.9 kg      目标体重 69.1 kg
安全速率        ≤ 0.39 kg 脂肪/周（体重的 0.5%）
预计周期        约 24 周（5.6 个月）   ← 这是「以月计」的事，不是「以周计」
```

**它顺带修正了一个算法错误**：蛋白目标以前按**总体重**算，现在按**瘦体重**算——
因为脂肪组织不需要蛋白质。

| | 按体重（旧） | 按瘦体重（新） |
|---|---|---|
| 78kg / 体脂 22% | 78 × 1.8 = **140 g** | 60.8 × 2.2 = **134 g** |

差 7g 看着不多，但它会把你推向高钠高热的餐品（脆汁鸡 1343mg 钠、安格斯 897mg 钠），
**反而拖慢腹肌进度**。

### 💧 三、水潴留指数（腹肌的隐形敌人）

这是"麦当劳出腹肌"最尖锐的矛盾，也是本项目独有的一个维度。

高体脂时腹肌被**脂肪**盖住；低体脂时腹肌可能被**水**盖住——钠摄入过高会导致皮下水分滞留，
**即使体脂达标，照镜子也是"平"的**。文献共识：钠、碳水等引起的水潴留可以在**一夜之间掩盖 2~3 周的减脂进展**。

工具按钠摄入估算滞留水量与"腹肌清晰度"：

```
每日钠摄入      3400 mg（你提供的实际摄入）
钠致滞留水      约 0.42 L（占体重 0.54%）
腹肌清晰度      【明显发糊】
     皮下水分把腹肌线条泡软了——即使体脂达标，看起来也会「平」。
```

**这正好卡在麦当劳的软肋上**：要把蛋白吃够就得上脆汁鸡/安格斯（钠 900~1400 mg/份）；
要控钠就只能选玉米杯/牛奶/美式，蛋白又不够。**两个目标在麦当劳餐单上正面冲突。**

### 🍔 四、餐次填空（任意餐次组合）

**核心问题：只有部分餐次在麦当劳吃，该怎么配？**

不是"全天"或"补差"这两种固定模式，而是**任意餐次组合**——C(3,1)+C(3,2)+C(3,3) = **7 种**：

```bash
# 全天三餐都在麦当劳
--solve breakfast,lunch,dinner

# 只配早餐（午餐晚餐已知）
--solve breakfast --known "午餐=800,30,1200" --known "晚餐=700,35,1000"

# 配早餐+午餐（晚餐已知）
--solve breakfast,lunch --known "晚餐=700,35,1000"

# 早餐已吃、晚餐计划吃 → 只配午餐
--solve lunch --known "早餐=520,18,900" --known "晚餐=700,35,1000"
```

`--known` 的"已知餐次"**既能是已吃、也能是计划吃**——两者都占用额度，数学上等价。
格式 `名称=热量,蛋白[,钠]`，可重复传入。

**额度分配规则：**
```
剩余额度 = 全天目标 − 已知餐次合计
待解餐次标准份额 = 全天目标 × 该餐次权重（早 25% / 午 40% / 晚 35%）
scale = clamp(剩余额度 ÷ 待解餐次标准份额合计, 0, 1.30)
  剩余多 → 等比放大（方案随已知餐次变化，额度用得上）
  剩余少 → 等比压缩
  上限 1.30 → 单餐不超过自然份额的 1.3 倍，只配一餐时不吞掉全天额度
```

> **v2.4.0 修掉的缺陷**：旧逻辑是 `剩余 ≥ 标准份额 → scale = 1`，
> 于是「已知合计 ≤ 全天 − 标准份额」的**整段区间内方案完全不变** ——
> 改了早餐/午餐却看不到任何变化，会被当成页面坏了；
> 而且剩余额度永远用不上，全天合计系统性低于目标。
> 现在改成按剩余额度等比缩放并夹上限，**两个问题一起解决**。

**实测输出**（只配早餐，午晚已知）：

```
【已知餐次】（不配麦当劳，仅占用额度）
  · 午餐        800 kcal｜蛋白  30 g｜钠 1200mg
  · 晚餐        700 kcal｜蛋白  35 g｜钠 1000mg
  合计         1500 kcal｜蛋白  65 g｜钠 2200 mg

【麦当劳待配餐次 · 额度分配】
  剩余额度     524 kcal｜蛋白 81 g（= 目标 − 已知）

【早餐】目标 506 kcal / 蛋白 37 g
  · 原味板烧鸡腿炒双蛋堡   419 kcal  蛋白 27g  钠  715mg
  · 冰奶铁小杯              86 kcal  蛋白  5g  钠   44mg
  小计：505 kcal｜蛋白 32g｜脂肪 25g｜碳水 38g｜钠 759mg

【全天合计】（已知餐次 + 麦当劳配餐）
  热量      2005 / 2024 kcal     剩余 19
  蛋白        97 / 146 g        缺口 49
  钠        2959 / 2000 mg      ❌ 超上限 959 mg
```

**三个刻意的设计：**

1. **只配一餐时不会吃光全天额度** —— 早餐额度按"全天目标 × 25%"给，
   不会因为午晚已知就把剩余 1300 kcal 全塞进早餐。
2. **额度不足时给硬约束，不是硬凑** —— 组合总热量**不得超过该餐次额度的 115%**。
   若真配不出来（额度太紧），给最低热量兜底并**如实标注超出多少**，不静默超标。
3. **已知超标会直说** —— 已知餐次已超目标时，直接告诉你"今天已无法达成目标"，
   只给最低热量建议，不假装还能补救。

**求解方法论**（不是拍脑袋，是词典序优化）：
1. 热量贴合目标（偏离 >15% 直接淘汰 —— 硬约束）
2. 在此前提下最大化蛋白
3. 同分时选低钠、高蛋白密度

**提供两种模式**，因为一个方案满足不了两个互斥目标：
- **蛋白优先** — 蛋白最大化，钠会超标
- **控钠优先** — 钠压进 2000mg，蛋白大幅让步

### 🎫 五、券联动（最优惠优先 + 临期加分）

把券仓快照喂给配餐引擎，它会**偏好带临期券的餐品**，把快过期的券优先用掉。

```bash
python scripts/meal_planner.py --weight 78 --height 175 --age 40 --sex male \
    --activity light --target-weight 72 --weeks 12 --bmr 1750 \
    --coupons data/coupon-snapshot.sample.json
```

**实测输出：**

```
券使用情况
  🎫 9.9元中杯冰美式  ¥11.90 → ¥9.90  省 ¥2.00（2026-10-16 23:59 到期）
  ─────────────────────────
  本次方案用券 1 张，立省 ¥2.00

  ⏰ 临期券提醒（方案未用上，建议尽快处理）：
     · 人气麦旋风买一送一  2026-10-11 23:59 到期
     · 火腿扒堡早餐两件套  2026-10-12 10:29 到期

  ❌ 被排除的券（1 张，不计入优惠）：
     · 免费脆薯饼  —— 计价实测不可用
```

**但省钱不是全部——它会把代价也摆出来：**

```
────────────────────────────────────────────
用券的代价（对比不用券的方案）
────────────────────────────────────────────
  蛋白 -2 g｜热量 +8 kcal｜钠 +118 mg｜省下 ¥+2.00
  ⚠️  用券省了钱但牺牲了蛋白。若该券优惠额不大，
     建议把它单独用掉（比如只买那杯咖啡），不挤进正餐方案。
────────────────────────────────────────────
```

**为什么非要报这个代价**：那张冰美式券绑的是 14 kcal / 1g 蛋白的饮品，
用它就得挤掉一份高蛋白饮品。**只报"省了 ¥2"是报喜不报忧。**

**三条硬性规则：**
1. **临期越紧优先级越高** —— urgency 分档（24h 内 1.0 / 3 天内 0.6 / 7 天内 0.3），已过期券不再激励
2. **不可用的券不计入优惠** —— 标记 `unavailable` 的券只提示，不算省钱
3. **必须报出代价** —— 同时算一份不用券的方案做对比

#### 这一路上踩到的三个真坑

**坑 1：自提和外送是两套完全不同的商品编码，还没有映射规则**

| 商品 | 自提编码 / 价格 | 外送编码 / 价格 |
|---|---|---|
| 双层吉士汉堡 | `1120` / ¥23.00 | `901120` / **¥25.00** |
| 中薯条 | `4810` / ¥14.00 | `501205` / **¥15.50** |
| 麦咖啡美式 | `507411` / ¥11.90 | `507368` / ¥11.90 |

看着像 `9 + 补零`，但「不素之霸双层牛堡」自提 `4648` 对外送 `900138`，**规则直接失效**。
所以必须按名字在两个渠道菜单里分别查，不能靠编码推导。

**坑 2：计价接口会「静默丢弃」渠道不可售的商品**

拿自提编码去外送渠道试算，接口返回：

```json
{ "success": true, "code": 200, "productList": [ { "productCode": "507411", ... } ] }
```

**`success: true`，但请求的 3 件商品只剩 1 件**——汉堡和薯条被悄悄删掉了。
如果只看 `success` 就下单，用户会收到一份缺货订单。

**本工具的做法：逐项比对 `productList` 与请求清单，不一致就报警。**

**坑 3：券标签说「外送专用」，不代表外送编码能被券命中**

那张 9.9 元冰美式券的标签明写「到店专用、外送专用」，但用外送编码 `507368` 计价直接报错：

```
code 600012 · 促销规则不支持该商品
```

券绑定的是自提编码 `507411`。**券必须逐渠道单独试算，不能信标签。**

> 因此改用**本地虚拟角色**替代——有陪伴感，零隐私风险。

### Hero 上为什么不放「297 项回归测试」

最初 hero 的四个数字是：**158 项营养数据 / 251 项回归测试全通过 / 7 种餐次组合 / 9 个开发中修复的真缺陷**。
后来发现两个问题：

1. **数字是写死的，已经过期** —— 实际早已是 297 项测试、10 个缺陷，页面却还显示旧值。
   这类"硬编码的进度数字"必然腐烂，而且没人会去检查首页。
2. **它们是内部工程指标，不是用户价值。** 第一次来的人关心的是
   "这个工具能帮我做什么"，而不是作者写了几条测试。
   放上去反而像自证清白，会削弱主张。

现在改成：

| 位置 | 内容 | 为什么 |
|---|---|---|
| Hero 统计 | `158` 项官方营养数据 | 说明结论来自真实数据，不是拍脑袋 |
| | `3` 种目标模式 | 我能选什么 |
| | `7` 种餐次组合 | 我能怎么用 |
| | `✓` 真实下单已跑通 | 端到端真的通了（这条不是数字，是事实） |

**四个数字里三个由脚本算出**（营养表条数、目标模式数、餐次组合数），
模板里写 `__ITEM_COUNT__` / `__GOAL_COUNT__` / `__COMBO_COUNT__` 占位符，
`tools/build_demo.py` 生成时注入：

```python
def hero_stats(rows, common):
    """页面上展示的数字，一律由数据算出，禁止手写。"""
    return {
        "__ITEM_COUNT__": len(rows),
        "__GOAL_COUNT__": len(mp.GOALS),
        "__COMBO_COUNT__": 2 ** len(DEMO_MEALS) - 1,   # C(3,1)+C(3,2)+C(3,3)
    }
```

而且校验是**双向**的：模板里出现的每个占位符必须在脚本里有值，
脚本里算出的每个也必须在模板里真的用到 ——
否则说明数据没被展示，同样是漂移。

**回归测试数、缺陷数这些工程指标，留在 README 里给评审看就够了。**

**同一条规矩也适用于仓库描述。** GitHub 的 About 里曾写着「含 65 项回归测试」，
实际早已是 297 项 —— 和 hero 犯了**同一个错**：手写的进度数字必然腐烂，
而仓库描述**没有任何自动同步机制**，比 hero 藏得更深。
报名成功后才发现，已删除，只留价值主张与参赛声明。

**判断标准很简单：一个数字如果需要人记得去改，那它迟早会是错的。**

### 按钮为什么叫「生成方案」而不是「重新计算」

这是个很小的改动，但值得记下判断依据，免得以后又改回去。

**「重新计算」的问题是字面承诺了一件不存在的事**：它暗示"有一个旧结果需要重算"。
但页面的结果是**实时**的 —— 改一个滑块、填一个数字，右侧方案当场就变了。
于是用户点下去时**找不到任何新旧对比**，必然以为按钮坏了
（这个误判在开发过程中真实发生过两次）。

改名的逻辑：

| 候选 | 问题 |
|---|---|
| 重新计算 | "重新"预设了旧结果，与实时渲染矛盾 ✅ 已弃用 |
| 计算 | "算"是过程词，不说明产出什么；第二次点又觉得重复 |
| **生成方案** | **指向产出物**；第一次用=生成、之后用=再生成，两个状态都通顺；且与页面已有的「📋 生成点餐清单」构成同一动词家族 |

**没有采用"按钮文案随状态变化"**（首次「计算」、之后「重新计算」）——
状态相关的文案会让用户以为两个按钮是两件事，且首次/非首次的切换点难以察觉。

配套调整：面板提示改为「所有参数**实时生效**，右侧随改随更新；下方按钮用于跳转查看」
—— 按钮文案与提示必须口径一致，否则一个说"生成"、一个说"实时"，用户还是懵。

### 时段提醒：只提醒，不替用户改方案

**清单是在 16:00 生成的，却包含早餐专供商品** —— 这本来是个缺陷，但处理方式很重要：

**不要去"自动修正"用户的方案**，因为你无法知道他是现在要吃、还是为明早备餐。
正确做法是**把冲突说出来，让用户自己决定**：

```
── ⚠️ 时段提醒 ──
本清单含早餐时段商品：原味板烧鸡腿炒双蛋堡
麦当劳早餐一般 05:00–10:30 供应（各门店略有差异），当前时间 16:16 已过早餐时段。
· 若为明早备餐 → 直接按本清单下单，记得【预约早餐时段】
· 若现在就要吃 → 需替换上述商品，其余餐次不受影响
```

**关键词是按证据定的，不是凭印象**。2026-10-11 实测（门店 `1410509` 双菜单对照）：
当前 15:59 菜单里完全没有「麦满分系列 / 炒双蛋堡系列 / 早安营养卷」三个类目，
次日 07:30 预约菜单里都有 → 这三个才是早餐时段专供。

> ⚠️ **刻意不收录「厚松饼」**：`521730` 枫糖风味厚松饼猪柳蛋堡在**当前菜单里就存在**、
> 外送菜单还标「全天供应」。把它当早餐关键词会造成误报。

清单末尾还会把判定方法写给 Skill：

```
若某餐品在菜单里查不到，先判断是「下架」还是「时段限定」——
用 query-meals 的 reservationDate 拉对应时段菜单做对照，
对照后仍无同名商品才算下架，不得用相近商品顶替。
```

### 渠道提醒：自提与外送的差异不止编码

清单里固定附一段渠道提醒，因为**同一商品在两个渠道的在售情况都可能不同**：

```
── 📦 渠道提醒（自提 vs 麦乐送）──
· 两个渠道是两套商品编码，且【在售情况可能不同】，必须按渠道各查一次
  实测：麦咖啡™冰奶铁中杯 自提有售（507409），外送菜单里只有热奶铁（507328）
· 同一商品外送价通常更高（实测：板烧鸡腿堡 自提 ¥24 / 外送 ¥26）
· 不要跨渠道复用商品编码
```

> 实测数据来自门店 `1410509`：自提 `1406` ¥24 的板烧鸡腿堡，外送是 `901406` ¥26。
> **不能拿自提价替外送报价，也不能假定"换个渠道照样能买"。**

### 营养数据查不到就说查不到

官方营养表只有 **158 项，不覆盖全部在售商品**。
遇到表里没有的商品（例如外送菜单的「枫糖风味厚松饼猪柳蛋堡」），
最省事的错误做法是"找个相似的填上"——那就成了编数据。

所以把「查不到」做成了一个**有退出码的确定性结果**：

```bash
$ python scripts/nutrition_lookup.py 板烧鸡腿堡
✅ 命中（精确匹配）
  板烧鸡腿堡  391 kcal｜蛋白 23g｜脂肪 17g｜碳水 35g｜钠 1041mg

$ python scripts/nutrition_lookup.py 枫糖风味厚松饼猪柳蛋堡
❌ 查不到：『枫糖风味厚松饼猪柳蛋堡』不在官方营养表（158 项）内

   本项目铁律：**不得估算、不得用相近商品替代**。
   请如实告知用户「该商品没有营养数据」，并可请他提供包装标注。

   表中名称相近的项（仅供你了解表里有什么，**不得直接当作替代品**）：
     · 猪柳炒双蛋堡  437 kcal｜蛋白 25g｜钠 705mg
     · 猪柳蛋麦满分  308 kcal｜蛋白 16g｜钠 781mg
$ echo $?
2
```

**退出码 2 是关键** —— 调用方没法含糊过去。相近项会列出，但明确标注
「仅供参考，不得直接当作替代品」：**把信息摊开，把决定权留给用户。**


复制它，发给 WorkBuddy，Skill 就会用你的 MCP 凭证完成真实下单。

### 为什么网页不能直接下单

不是没做，是**不该做**：

| 障碍 | 说明 |
|---|---|
| **凭证暴露** | 下单请求要带 `Authorization: Bearer <你的token>`。写进前端 = 任何人 F12 就能拿到，等于把下单权限公开 |
| **跨域** | `mcp.mcd.cn` 是服务端 MCP 端点，不会给浏览器页面开 CORS |
| **资金风险** | 纯前端下单意味着任何人都能用你的账号花钱 |

所以边界划在这里：**网页负责算（零依赖、零凭证、零风险），Skill 负责下单（持凭证、有确认流程）。**

> 交接清单里**不含任何 Token**。下单时餐品名要通过 `query-meals` 实查商品编码，
> 且**自提与外送是两套编码**（实测：双层吉士汉堡 自提 `1120` / 外送 `901120`），
> 必须按渠道各查一次。**金额未经你确认，不会调用 `create-order`。**

## 🔬 开发过程中修掉的 10 个真实 Bug

这个项目不是一次写成的。以下是开发中真实发现并修复的缺陷——**保留它们，因为它们是这个工具可信度的证据**：

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | 营养表加载 **0 项**，方案全空 | CSV 带 BOM，首列名变成 `\ufeffname` | 改用 `utf-8-sig` |
| 2 | 午餐出现 **两杯热奶铁** | 无同类去重约束 | 加同分类互斥 |
| 3 | **巨无霸/麦香鸡/麦香鱼**被排除 | 子串匹配用「堡」判断，这三个名字不含「堡」 | 改显式白名单 |
| 4 | **V翅被当成饮品** | 名字含「柠」字，命中饮品关键词 | 改显式白名单 |
| 5 | 差额拆解**三项加总对不上总额** | 券收益项符号写反（券让自提更便宜，应为加项），导致 `3.50+7.90-2.00=9.40 ≠ 13.40` | 改为 `best券省 − worst券省`，并加自洽校验 |
| 6 | 腹肌可见度分级**在 20-25% 段错位一档** | 我把来源表格里"20-25% 极微弱轮廓"误写成"基本平坦"，与 25%+ 档语义重复 | 逐档对照来源重排，并补 9 项边界测试固化 |
| 7 | 体成分引擎**直接崩溃** | `build_body_plan` 正常路径返回单个 dict，错误路径返回 `(None, [错误])` 二元组，调用方按二元组解包即 `ValueError` | 统一返回签名，加类型一致性测试 |
| 8 | 测试汇总**漏统计 37 项** | `run_all.py` 只认"测试结果："前缀，新套件用"结果："，静默少算 | 改用正则匹配任意位置，并对无法识别的汇总行报警 |
| 9 | 额度极紧时给出**超预算 5 倍**的方案 | `pick_meal` 只靠打分函数的软惩罚抑制超标，没有硬约束；剩余额度 100 kcal 时仍返回 567 kcal 的组合 | 加 `hard_cap` 硬过滤 + 无解时兜底最低热量并如实标注 |
| 10 | **改了已知餐次但方案完全不变** | 额度分配写成 `剩余 ≥ 标准份额 → scale = 1`（"不超发"）。于是待解餐次目标只由全天目标决定，**与已知餐次无关**；且剩余额度永远用不上 | 改为 `scale = clamp(剩余 ÷ 标准份额, 0, 1.30)`，既响应已知、又用得上额度，同时用上限防止单餐吞掉全天 |

缺陷 3 尤其严重：**三个招牌汉堡完全没进候选池**，等于把最优质的主食选项排除在外。
缺陷 5 是靠**手工验算**发现的——输出看着合理，但加总不对。现已在输出中内建校验，
三项之和与总差额偏差超过 0.02 元会直接打印警告。

**缺陷 8 值得单独说**：它没有报错，只是让测试总数从真实的 203 悄悄变成 166。
如果不是顺手核对了"各套件相加是否等于总计"，这个漏洞会一直躺着——
**自动化本身也需要被验证。**

另外记一次**反向的教训**：写腹肌分级测试时，边界用例失败，我第一反应是"实现错了"，
核对来源后才发现是**测试期望写反了**（区间语义是 `[lower, upper)`，`bf=12` 属于 12-15 档）。
**先怀疑自己、再改实现**，比反过来安全。

**缺陷 10 值得单独说**，因为它同时踩了两个坑：

1. **表现形式像"页面坏了"，实际是公式决定的必然结果。**
   已知合计在「≤ 全天目标 − 待解餐次标准份额」的整段区间内，方案一模一样。
   用户在这个区间里改数字，当然看不到任何变化。
2. **旧测试正在固化这个 Bug。** `test_slots.py` 里那条断言
   「早餐额度 ≤ 标准份额」，期望值写的**就是**要被修掉的规则 ——
   所以修复时它失败了，而**这次失败是对的**。
   **断言失败要先分清：是实现错了，还是断言在保护一个过时行为。**

修完还补了一道**突变测试**：故意把 JS 改回旧规则，确认对拍立刻报
`✗ 用例#0 [scale] JS=1 Python=1.3` + 餐品列表不一致。
**只跑一遍"通过"不能说明覆盖到了改动分支，要主动注错验证。**

- 早餐已吃、晚餐有计划，**午餐临时要在麦当劳解决**的人
- 算过 TDEE/BMR 但不知道"这个热量在麦当劳能吃到多少蛋白"的人
- 关心**体脂率而非体重**、想知道"离看得见腹肌还有多远"的人
- 手里一堆券，想知道**哪张最优惠、哪些快过期该马上用掉**的人
- 需要有人盯着才不破戒的人
