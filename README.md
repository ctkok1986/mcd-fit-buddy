## 😤 先说一个反直觉的事实

市面上所有"麦当劳减脂助手"都在做同一件事：给你一份看起来合理的低卡餐单。

**但它们几乎都不告诉你：这份餐单哪里是补不上的。**

我们拿官方营养接口的 **158 项餐品数据**做了一次完整的可行域求解，结果是这样：

**一个 78kg / 175cm / 40 岁的男性，目标是 12 周减到 72kg：**

| | 蛋白优先 | 控钠优先 |
|---|---|---|
| 全天热量 | 1846 kcal ✅ | 1857 kcal ✅ |
| 蛋白质 | **128 g**（目标 140） | **92 g**（目标 140） |
| 钠 | **3488 mg** ❌ | **1941 mg** ✅ |

WHO 建议每日钠摄入 **< 2000 mg**。

**两个方案没有一个能同时满足「热量达标 + 蛋白达标 + 钠达标」。**

这不是算法没调好——这是**麦当劳餐单的结构性事实**：菜单里高蛋白的选择（脆汁鸡、安格斯牛堡）钠含量都极高，而低钠的选择（玉米杯、牛奶、美式）热量和蛋白都低。

**本项目的立场：与其给一份粉饰过的餐单，不如把这个矛盾摊开给你看，让你自己选。**

## ✨ 四个能力

### 🍔 一、配餐求解

填入参数 → 算出目标 → 真实求解三餐：

| 参数 | 参数 |
|---|---|
| 体重 / 身高 / 年龄 / 性别 | 活动强度（5 档） |
| 目标体重 | 期望周期（周） |

**计算链路：**
```
Mifflin-St Jeor 公式 → BMR
BMR × 活动系数 → TDEE
(减重 × 7700) ÷ 天数 → 每日缺口
  ├─ 护栏 A：缺口 ≤ TDEE × 25%
  └─ 护栏 B：摄入 ≥ BMR × 1.1
→ 热量目标 + 蛋白目标（1.8 g/kg）+ 脂肪下限（0.6 g/kg）
→ 三餐槽位求解（早餐 25% / 午餐 40% / 晚餐 35%）
```

**求解不是拍脑袋，是词典序优化：**
1. 热量贴合目标（偏离 >15% 直接淘汰）
2. 在此前提下最大化蛋白
3. 同分时选低钠、高蛋白密度

**提供两种模式**，因为一个方案满足不了两个互斥目标：
- **蛋白优先** — 蛋白最大化，钠会超标
- **控钠优先** — 钠压进 2000mg，蛋白大幅让步

#### 这一路上踩到的三个真坑

**坑 1：自提和外送是两套完全不同的商品编码，还没有映射规则**

| 商品 | 自提编码 / 价格 | 外送编码 / 价格 |
|---|---|---|
| 双层吉士汉堡 | `1120` / ¥23.00 | `901120` / **¥25.00** |
| 中薯条 | `4810` / ¥14.00 | `501205` / **¥15.50** |
| 麦咖啡美式 | `507411` / ¥11.90 | `507368` / ¥11.90 |

看着像 `9 + 补零`，但「不素之霸双层牛堡」自提 `4648` 对外送 `900138`，**规则直接失效**。
所以必须按名字在两个渠道菜单里分别查，不能靠编码推导。

**坑 2：计价接口会「静默丢弃」渠道不可售的商品**

拿自提编码去外送渠道试算，接口返回：

```json
{ "success": true, "code": 200, "productList": [ { "productCode": "507411", ... } ] }
```

**`success: true`，但请求的 3 件商品只剩 1 件**——汉堡和薯条被悄悄删掉了。
如果只看 `success` 就下单，用户会收到一份缺货订单。

**本工具的做法：逐项比对 `productList` 与请求清单，不一致就报警。**

**坑 3：券标签说「外送专用」，不代表外送编码能被券命中**

那张 9.9 元冰美式券的标签明写「到店专用、外送专用」，但用外送编码 `507368` 计价直接报错：

```
code 600012 · 促销规则不支持该商品
```

券绑定的是自提编码 `507411`。**券必须逐渠道单独试算，不能信标签。**

## 🚀 快速开始

### 1. 申请麦当劳 MCP Token

前往 **[open.mcd.cn/mcp](https://open.mcd.cn/mcp)** → 手机号登录 → 右上角「控制台」→「激活」→ 复制 Token。

### 2. 配置 MCP 连接器（以 WorkBuddy 为例）

左侧边栏【专家·技能·连接器】→【连接器】→【自定义连接器】→【配置 MCP】：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer YOUR_MCP_TOKEN"
      }
    }
  }
}
```

### 3. 装 Skill + 跑引擎

```bash
# 复制到技能目录
cp -r mcd-fit-buddy ~/.workbuddy/skills/mcfit-buddy

# 本地跑配餐求解（不需要 Token）
python scripts/meal_planner.py \
  --weight 78 --height 175 --age 40 --sex male \
  --activity light --target-weight 72 --weeks 12 --mode both
```

### 4. 开聊

```
你：我 78 公斤，175，40 岁，想 12 周减到 72，一周练两次
搭子：你的 BMR 1679 kcal，TDEE 2308 kcal，每日摄入目标 1847 kcal，
      蛋白目标 140g。

      ⚠️ 先说一个坏消息：在麦当劳餐单上，你这三个目标没法同时达成。

      蛋白优先方案：128g 蛋白 / 钠 3488mg
      控钠优先方案： 92g 蛋白 / 钠 1941mg

      选哪条路？剩下的蛋白缺口建议用无糖希腊酸奶补。
```

## 🔬 开发过程中修掉的 5 个真实 Bug

这个项目不是一次写成的。以下是开发中真实发现并修复的缺陷——**保留它们，因为它们是这个工具可信度的证据**：

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | 营养表加载 **0 项**，方案全空 | CSV 带 BOM，首列名变成 `\ufeffname` | 改用 `utf-8-sig` |
| 2 | 午餐出现 **两杯热奶铁** | 无同类去重约束 | 加同分类互斥 |
| 3 | **巨无霸/麦香鸡/麦香鱼**被排除 | 子串匹配用「堡」判断，这三个名字不含「堡」 | 改显式白名单 |
| 4 | **V翅被当成饮品** | 名字含「柠」字，命中饮品关键词 | 改显式白名单 |
| 5 | 差额拆解**三项加总对不上总额** | 券收益项符号写反（券让自提更便宜，应为加项），导致 `3.50+7.90-2.00=9.40 ≠ 13.40` | 改为 `best券省 − worst券省`，并加自洽校验 |

缺陷 3 尤其严重：**三个招牌汉堡完全没进候选池**，等于把最优质的主食选项排除在外。
缺陷 5 是靠**手工验算**发现的——输出看着合理，但加总不对。现已在输出中内建校验，
三项之和与总差额偏差超过 0.02 元会直接打印警告。
