# 套餐 vs 单点：实测记录与改造依据

> 实测时间：2026-10-13 00:16（凌晨，用 24h 门店 `1410098` 福州盛世茶亭餐厅）
> 数据来源：`query-meals` / `query-meal-detail`（MCP 真实返回，非推测）

---

## 一、问题（本项目此前的真实缺陷）

配餐引擎的候选池**只有单品**——`data/nutrition.csv` 的 158 项，
全部来自 `list-nutrition-foods`，**里面一条套餐都没有**。

结果：工具推荐的方案全是单点组合，而麦当劳的主力消费场景是**套餐**。
对性价比敏感的白领/学生党来说，这个推荐是**不成立的**。

**实证**：`examples/first-real-order-2026-10-11.md` 里那次真实下单：

```
板烧鸡腿堡         ¥26.00   ← 单点
麦咖啡冰美式中杯    ¥19.00 → ¥9.90（用券）
实付 ¥43.00
```

买的是纯单点。而同一家店（茶亭店）的「板烧鸡腿堡四件套」只要 **¥28**。

## 三、营养怎么算？（技术可行性已验证）

**套餐的营养 = 各轮次选中项的营养之和。**

以「板烧鸡腿堡四件套」（code `9900000890`）为例，`query-meal-detail` 返回
**4 个 rounds**：

| Round | 名称 | 默认选项（isDefault=1） | code |
|---|---|---|---|
| 1 | 板烧鸡腿堡 | 板烧鸡腿堡 | `1406` |
| 2 | 小食 | 中薯条 | `4810` |
| 3 | 小食 | 麦乐鸡4块 | `515106` |
| 4 | 饮料 | 可乐中杯 | `3050` |

这些 code **全部能对应到 `nutrition.csv` 里的单品**：

| 组成 | kcal | 蛋白 | 钠 |
|---|---|---|---|
| 板烧鸡腿堡 | 391 | 23 | 1041 |
| 中薯条 | 289 | 4 | 165 |
| 麦乐鸡4块 | 170 | 10 | 337 |
| 可乐中杯 | 147 | 0 | 0 |
| **合计** | **997** | **37** | **1543** |

→ **套餐与单点是同一批单品，营养必然相同，差别只在价格。**

### 每轮可换（`diffPrice` 给出差价）

Round 4（饮料）的例子：

```
可乐中杯        +¥0     ← 默认
无糖可口可乐中杯  +¥0     ← 换这个：少 147 kcal，不加钱
锡兰红茶        +¥0
纯牛奶          +¥1
麦咖啡™冰美式中杯 +¥9
```

→ **同样是 ¥28，选「无糖可乐」比「可乐」少 147 kcal，加价 0 元。**
这是套餐维度独有的优化空间：**价格不变、营养可变**。

## 四、⚠️ 套餐的真实局限（不能只讲好话）

**套餐是打包的，营养灵活度低。** 上面那份四件套：

- 热量 997 kcal —— 占全天目标（2124）的 **47%**
- 蛋白 37 g —— 只占目标（146 g）的 **25%**
- **钠 1543 mg —— 占上限（2000）的 77%**

**钠是打包商品里最贵的成分**：薯条 165 + 麦乐鸡 337 = 502 mg，
几乎白送一半的钠配额，换来的蛋白只有 14 g。

所以套餐**不能无脑用**——正确用法是：

- ✅ **省钱的场景**：本来就要吃薯条 + 小食的那一餐（用套餐替代单点，省一半）
- ❌ **不该用的场景**：为了省钱硬塞一份不需要的薯条，钠先超标

**这正是"性价比 vs 营养"的真实冲突，工具应该把它摊开给用户选，而不是替用户决定。**

## 五、改造方向（待定）

候选池从「单品」扩展为「单品 + 套餐」，架构上分两层：

| 层 | 数据 | 来源 | 更新频率 |
|---|---|---|---|
| **营养** | 套餐 = 组成品营养之和 | 本地 `nutrition.csv` 算 | 稳定（单品营养少变） |
| **价格** | 套餐现价 / 换品差价 | MCP `query-meals` + `query-meal-detail` | 实时（价格常变） |

**必须注意的坑**：

1. **套餐组成可能含营养表里没有的单品**（如新品「韩式烟熏芝士风味酱…」）。
   按项目既有原则：**查不到就说查不到，不得瞎算**。
2. **每个套餐要单独调一次 `query-meal-detail`** 才能展开。
   不要放进每次渲染的路径，应在构建期或按需缓存。
3. **不许把套餐价格写死进前端**——价格会变，写死必然腐烂
   （同《Hero 上为什么不放「297 项回归测试」》那条教训）。

## 六、⚠️ 门店级差异（2026-10-13 实测，必须先看这一节）

套餐数据**不是全国统一的，是门店级的**。用两个城市实测对比：

- A：福州茶亭 `1410098`（本快照的来源门店）
- B：北京建外SOHO(A座) `1950564`

### 价格差异 —— 很小

| 套餐 | 福州 | 北京 |
|---|---|---|
| 板烧鸡腿堡四件套 | ¥28.0 / 原¥57.0 | ¥28.0 / 原¥57.0 |
| 麦辣鸡腿堡四件套 | ¥28.0 / 原¥57.0 | ¥28.0 / 原¥57.0 |
| 人气超值四件套随心选 | ¥28.0 / 原¥57.0 | ¥28.0 / 原¥57.0 |
| 巨无霸三件套 | ¥37.0 | ¥36.5 |
| 吉士汉堡包套餐 | ¥26.5 | ¥26.0 |
| 麦乐鸡套餐 | ¥25.0 | ¥25.0 |
| 人气经典随心配 | ¥14.9 | ¥14.9 |

**现价差 ¥0~0.5，划线原价差约 ¥1。** 价格这块，快照的参考价值尚可。

### 但编码与可选内容是门店级的 —— 这才是要害

**① 编码不同**

| 商品 | 福州 code | 北京 code |
|---|---|---|
| 人气经典随心配 | `9900015187` | **`9900013304`** |
| 精选超值随心配 | `9900015188` | **`9900015568`** |

**② 可换选项不同**

同是「人气经典随心配」，北京店比福州店多出：

- 蓝区：**麦香鱼**（+¥0）、**那么大鸡排（椒盐风味）**（-¥1）
- 粉区：**小杯玉米杯**、**菠萝派**

（福州店没有这几项。）

**③ SKU 集合也不同**

北京店有「安格斯MAX厚牛堡」全系列、「开心乐园餐」多款、「鱼牛汉堡四件套」；
福州店有「泷泷星愿四件套」「泷运当头四件套」——**两边货架不一样**。

### 结论（写进代码与文档的硬规则）

| 数据 | 是否门店级 | 处理方式 |
|---|---|---|
| **单品营养** | ❌ 全国一致 | 可用本地快照 `nutrition.csv` |
| **套餐编码 / 可换选项 / 价格** | ✅ **门店级** | **必须实时取用户门店** |

```
query-nearby-stores / delivery-query-stores   # ① 定位用户门店（不要复用快照里的编码！）
query-meals(storeCode, orderType, beType)     # ② 拿该店套餐 code 与价
query-meal-detail(storeCode, code, ...)       # ③ 展开该店 rounds 与可选项
```

**`data/combos.json` 的定位就此明确：只用于演示页与离线估算，
不是「可以下单的依据」。** 页面必须显著标注它是示例价。
